# 北京平台资料导入（2026-09）

这是管理员显式执行的单次数据操作，不是 Flyway 数据迁移，也不会随部署自动运行。
私有 ZIP、中间 JSON、联系方式和数据库备份不得提交 Git。

## 数据边界

- 116 家单位进入会员管理，原始来源行保留。资料标记为入会申请的 15 家保持待审核，其余按提供的名录登记；这不是独立资质认证。
- 地址、联系人、统一社会信用代码等缺项留空，不生成占位身份、账号或密码。已有企业开户、资料草稿与审核流程保持不变。
- 产品和服务描述在「产品与需求 → 企业供给资料」展示，不编造已经审核上架的独立产品条目。
- 40 条政策标准进入政策目录，保存摘要、版本说明和原文链接，不冒充已归档全文。
- 5 家相关协会仅进入资料目录，不创建租户或跨协会共享授权。
- 50 条外部招投标在独立页签展示，不伪造会员需求或双方已确认的合作。截止时间按北京时间解释，资格与更正公告以来源原文为准。
- 目录接口要求认证及服务器核验的协会范围；没有游客公开发布。

## 安全检查与执行

1. 先部署包含 V30 的代码，确认服务健康。V30 只建表。
2. 将用户批准的原始 ZIP 放在仅维护账号可访问的临时位置，校验 SHA256：
   `03b0929d31d163f51461eb7f8011b14c356c02d4f7ccb5bdf2040103920f9daa`。
3. 管理员在服务器仓库运行 `sudo python3 tools/operations/apply_platform_dataset.py --archive /已核验的路径/source.zip`。默认只有只读预检。
4. 确认预检通过后，加 `--execute --confirm-source-sha256` 和上述完整校验和执行。固定维护账号没有数据库权限，不得以部署入口绕过。
5. 脚本先创建新的受保护业务库备份，再在单一事务和锁内重新预检、清理、导入、对数和记审计。账号、认证库和权限不修改。

清理只针对已人工对账的 35 个明确主记录 ID：5 家虚构企业、5 条供给、4 条需求、3 条政策、8 条匹配、4 条协作、2 条知识文档和 4 条政策影响分析。
有任何版本变化、账号绑定、额外业务依赖、真实名称冲突时停止。企业及大多数业务资料软删除，审计保留；政策影响分析和关联通知/待发送事件从活动表清理，备份可恢复。
重复运行通过导入回执识别，不重复创建 211 条来源记录。

## 验收及回滚

- 检查操作报告、116/40/5/50 条来源记录、待审核 15 家，以及演示主记录已退出活动查询。
- 刷新网页，清除或重新选择已经删除的演示企业上下文；抽查会员详情、供给资料、政策和外部公告。
- 代码回滚点不等于数据库回滚。若需撤销导入，先停止相关写入并评估导入后的真实变更，再以本次 `guanxian-before-*.dump` 做隔离恢复与差异核对；不要直接覆盖运行中的生产库。
- 临时上传包在校验和导入完成后再按精确路径清理；保护服务器备份与审计。

测试入口：`python tests/operations/platform_dataset_postgres_check.py`，只使用合成记录和自行创建的隔离 PostgreSQL 容器，验证预检、变更/绑定保护、事务回滚、账号和真实记录保留、完整导入、幂等重跑。
