# 可核对的业务回答 v1.2（本地开发版）

## 本次范围

实现顺序：服务端查询凭据 → 企业卡片与详情 → 企业对比 → 候选条件核对 → 协议、权限和浏览器验收。

不更换现有 Vue / Java / Spring AI 技术栈；没有引入 React UI 框架，没有新增数据库迁移，没有业务写入工具、正式匹配生成、MCP 或自动部署。本次没有提交、推送、创建 PR 或部署到生产。

## 数据链路

1. 后端创建本次请求专属的 `AssistantBusinessResults` 容器，经 Spring AI `ToolContext` 传递；个人模型路由仍使用同一个容器。
2. 只读工具使用服务端 `AssistantAccessContext` 及现有业务服务查询，模型不能提供用户角色、协会权限或 SQL。
3. 工具成功、拒绝、失败均生成凭据；输出由字段白名单构造，和模型回答文字分开。
4. 模型开始返回下一个片段时，已完成的查询凭据先发送，再发送文字；模型异常时补发已完成但未发送的凭据。工具执行中不宣称已经完成。
5. 无模型的确定性业务查询也返回同一契约，在本地结果状态事件中发送。政策知识库回答不伪造业务查询结果。
6. 前端校验版本、类型、UUID、时间、数量、字段、证据和大小限制，按查询 ID 合并；同一 ID 不允许中途改变内容。只有合法完成事件才将整轮标为完成。

每条凭据包含版本、查询 ID、类型、状态、组织上下文、可见范围说明、实际工具筛选参数、查询时间、实际总数和展示记录。全平台上下文的 `associationId` 可以为 null。当前可见范围可能包含权限允许的跨协会资料，不能把总数标成“本协会全部企业”。

状态区分 `OK / FORBIDDEN / FAILED / INVALID / UNAVAILABLE`；成功零条才是未找到记录，报错或无权限不是零条成功。

展示上限为每轮 8 次查询、每次 10 条；卡片单字段超过 300 字符明确标记截短。前端还有独立的结构和长度限制。超过展示数量时，总数和展示数分别显示；这不是完整数据导出。

## 用户界面

- 企业卡片：企业名、分类、能力、产品、服务、审核状态、更新时间；附实际范围、关键词、查询时间和数量。
- 查看详情：重新调用现有授权 `GET /members/{id}`，与会员企业页面共用 `MemberProfileDialog`。联系人等字段不进入卡片、对比或模型工具摘要，只在业务接口允许返回的详情中显示。
- 企业对比：选择 2–4 家，逐家重新读取；任何一家不可用或无权限，都不把部分旧资料拼成成功对比。表格支持窄屏横向滚动。
- 关闭详情/对比后回到原聊天位置；支持 Escape、焦点约束以及恢复触发按钮焦点。
- 已返回的卡片在文字断流后保留，但显示“文字解释尚未完成”，不会出现成功追踪提示。
- 用户、角色、协会或代管企业切换时，沿用原聊天清理机制，旧消息与附属弹窗一起移除。

卡片是本轮查询快照，不会因后台变化自动更新。详情和对比是点击时重新读取的当前授权档案。普通 DOM 文本转义，不执行 HTML，不接受模型提供的详情 URL。

## v1.1：明确对象的连续追问与可复制依据

- 从企业卡片点击“追问这家”，或者选择 1–4 家后点击“追问所选企业”。输入框上方持续显示对象，可逐家移除或清除选择；不会自动发送，也不覆盖已有草稿。
- 新请求字段 `selectedEnterpriseIds` 只包含有序 UUID，不发送卡片里的企业能力或联系人作为上下文。姓名只用于界面上的选择时快照；成功核验后，输入区名称更新为最新查询名称。
- 服务端先检查 `MEMBER_READ`，再逐家调用现有 `MemberService.get` 核对当前可见范围，生成专用 `SELECTED_MEMBERS` 凭据。每轮重新读取；任一家不可用就整组失败，不返回部分企业资料、不调用模型，也不从历史补齐。
- 凭据中的白名单资料进入当前模型提示，明确“这家/这几家”及顺序所指对象，标明资料不是指令。选择内容与顺序加入会话隔离键；前端改变选择还会启用新会话，减少跨对象历史混用。
- 前端在收到与所选 ID、顺序一致的凭据前不显示回答片段，完成事件必须再次包含同一凭据。旧后端忽略新字段时会明确报错，不降级成看似正常的追问回答。预查询计入每轮 8 次业务查询预算。
- 未接模型时也能核验所选企业并展示最新卡片/手动对比，但会明确说明“不进行自由问答推理”，不会把固定文字当成模型分析。
- 断流或主动停止后保留已完成凭据；重试使用原请求的对象快照。清空聊天、模型配置变化或登录身份/组织变化时清除选择。普通后续问题会保留对象，换话题可先清除选择。
- “复制结果与依据”输出纯文本快照，包含查询 ID、组织上下文、权限范围说明、筛选条件、时间、总数与展示数、企业 ID、字段和条件证据。附带非实时/非完整导出/资料不足说明；复制失败不显示成功标记。不会复制详情里的联系人字段，也不是一键复制整篇模型回答。

这是显式对象绑定和可核对数据链路，不是对真实模型“绝不跑偏”的保证。模型对条件和指代的理解仍需真实供应商验收；自然语言里提到未选择的新企业时，需要明确重新选择或澄清。

## v1.2：用户可编辑条件并重新核对

- 企业卡片的“按条件核对这家”及选择区的“按条件核对所选企业”支持 1–4 家企业。已有推荐凭据可点击“编辑这些条件并重新核对”；只带入所有企业共同且受支持的条件集合，不从模型文字猜测条件。
- 表单支持 1–8 项条件，每项最多 80 字，允许能力、产品、服务、分类、审核状态。状态用下拉选项，分类/状态精确核对，其余字段按保守字面规则核对。重复、空白、超长和未支持字段会被拒绝；不自动提交。
- 新增 `POST /api/v1/assistant/members/fit-check`：请求仅包含 `associationId`、有序 `enterpriseIds`、`criteria: [{field,value}]`。POST 是承载查询条件，不执行业务写入。服务端要求 `MEMBER_READ`，不能覆盖服务端已选协会，每个 ID 仍经现有 `MemberService.get` 校验。
- 接口复用 `explain_member_fit` 的字段白名单与规则，没有调用聊天模型或 RAG。返回 `{criteria,result}`，凭据类型为 `MEMBER_FIT_CHECK`，条件来源明确标为“用户手动确认”，响应 `Cache-Control: no-store`。
- 前端同时校验条件回显、企业 ID/顺序、逐项证据条件、证据登记值与返回档案字段的一致性。不一致不展示。任一企业无权限、不可用或读取失败时整组失败，不返回部分旧资料，不把失败记为未找到企业。
- 证据表按条件 × 企业展示“登记字段支持 / 登记值不同 / 资料不足”；不提供排名、总分或成功概率。结果只针对已选择的候选，不是全库搜索。点击核对重新读档案；改条件或移除企业会清除旧结果，防止条件与结果错配。
- 核对完成自动定位到结果，弹窗关闭按钮固定可见，支持 Escape、键盘焦点约束和手机横向表格。取消、关闭或身份切换后，迟到响应不得重新显示。复制结果保留组织、时间、范围、条件、证据和人工核验提示。

本版不把手动核对结果自动塞回模型会话，不保存表单到数据库，也不替用户发送消息或生成正式生态匹配。

## 新只读工具与推荐边界

`compare_member_enterprises(enterpriseIds)`：2–4 个不同的真实 UUID，逐家通过 `MemberService.get` 检查范围。工具只提供结构化对比数据；UI 打开表格时再次读取当前档案。

`explain_member_fit(enterpriseIds, criteria)`：1–4 家企业、1–8 个明确条件，只允许下列字段：

| 字段 | 本版规则 | 不支持时如何说明 |
| --- | --- | --- |
| 分类、审核状态 | 当前登记值精确相等 | 有不同值为“登记值不符合”；没有值为“资料不足” |
| 能力、产品、服务 | 展示的登记文字包含指定词 | 未提及、疑似否定表达均为“资料不足” |

支持证据、明确不符、资料不足分别展示原条件、依据字段、登记值及解释。自由文本核对是保守的字面规则，不是语义事实核验。资料截短可能导致证据不足，应打开详情继续核对。

自然语言条件由模型提取，页面明确标为“本轮工具参数”，供用户检查是否正确理解要求；系统没有证明模型一定理解了用户意图。模型禁用时可查询卡片并手动选择对比，但没有新增复杂自然语言推荐引擎。

不生成履约认证、采购结论、外部资质核验或成功概率；不把已有生态匹配记录的规则分数当作成功概率；不会调用写入型匹配生成接口。没有承诺穷尽所有候选、最优排名或自动补齐缺失资料。
